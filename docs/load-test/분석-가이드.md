# 매칭 부하 테스트 분석 가이드

이 문서는 `docs/load-test`의 k6 시나리오와 Grafana 대시보드를 기준으로, 매칭 V1 구조가 부하를 어떻게 받고 있는지 판단하기 위한 분석 기준을 정리합니다.

테스트는 두 종류로 나눕니다.

- 지속 유입 테스트: 일정 시간 동안 유저가 꾸준히 `joinQueue`에 진입하는 상황
- Spike 테스트: 짧은 시간에 유저가 한꺼번에 `joinQueue`에 진입하는 상황

두 테스트의 목적은 다릅니다. 지속 유입 테스트는 현재 구조가 운영 트래픽을 계속 처리할 수 있는지 확인하는 테스트이고, Spike 테스트는 순간 피크 이후 큐가 얼마나 빨리 정상 상태로 회복되는지 확인하는 테스트입니다.

---

## 1. 공통 분석 원칙

### 1.1 API와 매칭 엔진을 분리해서 본다

`joinQueue` API가 빠르다고 해서 매칭 시스템 전체가 빠른 것은 아닙니다.

`joinQueue`는 주로 다음 일을 합니다.

- 유저 상태 확인
- Redis 대기열 등록
- 티어별 ZSET에 티켓 저장

매칭 엔진은 별도 스케줄러에서 다음 일을 합니다.

- 전체 티어 대기열 로드
- FIFO 정렬
- 슬라이딩 윈도우 후보 탐색
- Lua 원자 삭제
- 매칭 세션 생성
- 이벤트 발행

따라서 분석할 때는 항상 아래 두 축을 나눠야 합니다.

- API 진입 성능: 사용자가 매칭 버튼을 눌렀을 때 요청이 얼마나 빨리 처리되는가
- 엔진 처리 성능: 큐에 들어온 유저가 실제로 얼마나 빨리 매칭되는가

### 1.2 평균보다 p95와 추이를 우선 본다

평균 응답 시간은 일부 느린 요청을 숨길 수 있습니다.

부하 테스트에서는 아래 순서로 봅니다.

1. 에러율
2. p95
3. p99
4. 평균
5. 최댓값

p95는 대부분의 사용자가 체감하는 상위 지연을 보여주고, p99는 순간적인 병목이나 GC, Redis 지연, 락 경합을 확인하는 데 사용합니다.

### 1.3 단일 지표만 보고 판단하지 않는다

예를 들어 `match_queue_size`가 증가한다고 해서 무조건 API가 문제인 것은 아닙니다.

함께 봐야 하는 조합은 다음과 같습니다.

- `joinQueue` 요청 수 증가 + 큐 증가 + 매칭 성사 수 정상: 유입이 처리량보다 큰 상태
- `joinQueue` 요청 수 정상 + 큐 증가 + 스캔 시간 증가: 엔진 스캔 비용 문제 가능성
- 큐 증가 + 락 스킵 증가 + 매칭 성사 수 감소: 멀티 인스턴스 락 경합 또는 스캔 주기 문제 가능성
- 원자 제거 실패율 증가 + 큐 감소 둔화: 취소/중복 처리/동시성 경합 가능성
- API p95 증가 + 엔진 지표 정상: API/Redis write/인증/DB 경로 문제 가능성

## 2. 핵심 지표 해석

### 2.1 joinQueue 초당 요청 수

의미:
- 초당 `POST /api/v1/match/join` 요청 처리량입니다.

보는 방법:
- k6에서 설정한 유입량과 Grafana의 실제 요청 수가 비슷한지 확인합니다.
- 두 API 인스턴스 전체 합산과 인스턴스별 요청 수를 모두 봅니다.

정상 신호:
- 설정한 유입량과 실제 요청 수가 크게 벌어지지 않습니다.
- `8080`, `8081` 두 인스턴스가 비슷하게 요청을 나눠 받습니다.

주의 신호:
- 설정한 유입량보다 실제 요청 수가 낮습니다.
- 한 인스턴스에 요청이 과하게 몰립니다.
- k6의 VU가 부족해 목표 rate를 못 맞춥니다.

### 2.2 joinQueue p95 응답 시간

의미:
- `joinQueue` 요청 중 95%가 이 시간 이하로 끝났다는 뜻입니다.

보는 방법:
- steady 테스트에서는 테스트 시간 내내 안정적인지 봅니다.
- spike 테스트에서는 피크 순간에 얼마나 튀고, 얼마나 빨리 내려오는지 봅니다.

판단 기준:
- p95가 낮고 안정적이면 API 진입 경로는 충분합니다.
- p95가 계속 상승하면 Redis write, 인증, DB 조회, JVM thread, connection pool 병목을 의심합니다.

### 2.3 joinQueue 에러율, 4xx 비율

의미:
- 에러율은 전체 HTTP 실패 비율입니다.
- 4xx 비율은 클라이언트 요청이 거절된 비율입니다.

보는 방법:
- 5xx는 시스템 장애 가능성이 높습니다.
- 4xx는 테스트 데이터 중복, 이미 대기 중인 유저, 인증 실패, 요청 스펙 오류 가능성이 높습니다.

판단 기준:
- 부하 한계 판단에서는 5xx를 더 중요하게 봅니다.
- 4xx가 높으면 성능 문제가 아니라 테스트 준비 상태가 잘못되었을 수 있습니다.

### 2.4 전체 대기 인원

의미:
- Redis 매칭 큐에 남아 있는 전체 유저 수입니다.

보는 방법:
- steady 테스트에서는 일정 수준에서 유지되거나 테스트 종료 후 감소해야 합니다.
- spike 테스트에서는 급격히 올라간 뒤 0에 가까워지는 시간을 봅니다.

판단 기준:
- 큐가 계속 증가하면 유입량이 매칭 엔진 처리량보다 큽니다.
- 테스트 종료 후에도 큐가 오래 남으면 엔진 처리량 또는 후처리 병목을 의심합니다.

### 2.5 초당 매칭 성사 수

의미:
- 초당 성사된 매칭 페어 수입니다.

보는 방법:
- `joinQueue` 초당 요청 수와 함께 봅니다.
- 이상적으로는 유저 2명당 1페어가 만들어집니다.

계산 예:
- 초당 100명 유입이면 이론상 최대 초당 50페어가 성사됩니다.
- 초당 매칭 성사 수가 50에 가깝고 큐가 증가하지 않으면 엔진 처리량이 유입을 따라가는 상태입니다.

주의 신호:
- 유입은 계속되는데 초당 매칭 성사 수가 낮습니다.
- 큐는 쌓이는데 매칭 성사 수가 오르지 않습니다.
- 스캔 시간은 증가하는데 성사 수가 증가하지 않습니다.

### 2.6 스캔당 로드 티켓 수

의미:
- 매칭 엔진 1회 스캔에서 Redis에서 읽어 온 티켓 수입니다.

보는 방법:
- 전체 대기 인원과 함께 봅니다.
- 큐가 많을수록 이 값도 커지는 것이 자연스럽습니다.

판단 기준:
- 이 값이 커질수록 전체 스캔 기반 V1 구조의 비용이 증가합니다.
- 티켓 수 증가에 비례해 스캔 시간이 크게 늘어나면 V2 최적화 후보입니다.

### 2.7 스캔 소요 시간

의미:
- 매칭 엔진이 1회 스캔에서 큐 로드, 정렬, 후보 탐색, 원자 삭제 시도를 수행하는 데 걸린 시간입니다.

보는 방법:
- p95와 p99를 봅니다.
- 스케줄 주기보다 스캔 시간이 길어지는지 확인합니다.

판단 기준:
- 스캔 시간이 짧고 안정적이면 엔진이 여유가 있습니다.
- 스캔 p95가 스케줄 간격에 가까워지면 다음 사이클이 밀릴 수 있습니다.
- 스캔 p99가 튀면 Redis, Lua, GC, 정렬 비용을 따로 봐야 합니다.

### 2.8 매칭 성공 유저 대기 시간

의미:
- 매칭이 실제로 성사된 유저가 큐에 들어온 뒤 매칭될 때까지 기다린 시간입니다.

보는 방법:
- p95를 가장 중요하게 봅니다.
- 클라이언트 수락 모달 시간 10초와 비교합니다.

판단 기준:
- p95가 10초에 가까워지면 UX 관점에서 위험합니다.
- p95가 10초를 넘으면 V1 구조가 해당 유입량을 안정적으로 처리하지 못한다고 봅니다.

주의:
- 아직 매칭되지 않고 큐에 남아 있는 유저는 이 지표에 포함되지 않습니다.
- 따라서 반드시 `전체 대기 인원`과 함께 봐야 합니다.

### 2.9 원자 제거 실패율

의미:
- 후보 페어를 찾았지만 Lua 원자 삭제가 실패한 비율입니다.

정상적인 실패 원인:
- 유저가 이미 `leaveQueue`를 호출함
- 다른 처리 흐름에서 이미 큐에서 제거됨
- 테스트 중 중복 요청 또는 상태 불일치 발생

판단 기준:
- join-only 부하 테스트에서는 거의 0에 가까워야 합니다.
- 실패율이 높으면 대기열 상태와 유저 상태의 정합성, 중복 join, 취소 흐름, 동시성 처리를 확인해야 합니다.

### 2.10 분당 락 스킵 수

의미:
- 다른 API 인스턴스가 매칭 엔진 락을 잡고 있어 이번 스캔을 건너뛴 횟수입니다.

보는 방법:
- 멀티 인스턴스 환경에서는 어느 정도 발생할 수 있습니다.
- 중요한 것은 락 스킵 자체가 아니라, 락 스킵이 큐 적체와 매칭 지연으로 이어지는지입니다.

판단 기준:
- 락 스킵 증가 + 큐 안정: 문제 아님
- 락 스킵 증가 + 큐 증가 + 매칭 대기 시간 증가: 엔진 실행 주기 또는 락 전략 조정 필요

## 3. 지속 유입 테스트 분석 가이드

지속 유입 테스트는 운영 중 유저가 꾸준히 매칭을 누르는 상황을 가정합니다.

현재 기본 시나리오는 3분입니다.

- 1,000명 / 3분
- 5,000명 / 3분
- 10,000명 / 3분

### 3.1 규모별 예상 유입량

| 규모 | 테스트 시간 | 유저 유입량 | 초당 유저 유입 | 이론상 필요 매칭 페어/s |
| --- | --- | ---: | ---: | ---: |
| 1,000명 | 3분 | 1,000명 | 약 5.6명/s | 약 2.8페어/s |
| 5,000명 | 3분 | 5,000명 | 약 27.8명/s | 약 13.9페어/s |
| 10,000명 | 3분 | 10,000명 | 약 55.6명/s | 약 27.8페어/s |

이 표는 최소 처리 기준입니다. 실제로는 티어 분포, 슬라이딩 윈도우, 스캔 주기 때문에 순간적으로 필요한 처리량이 더 커질 수 있습니다.

### 3.2 분석 순서

1. `joinQueue` 요청 수가 목표 유입량과 맞는지 확인합니다.
2. `joinQueue` 에러율과 4xx/5xx를 확인합니다.
3. `joinQueue` p95 응답 시간이 테스트 시간 내내 안정적인지 확인합니다.
4. `전체 대기 인원`이 지속적으로 증가하는지 확인합니다.
5. `초당 매칭 성사 수`가 이론상 필요 페어/s에 근접하는지 확인합니다.
6. `매칭 성공 유저 대기 시간 p95`가 10초 아래인지 확인합니다.
7. `스캔 소요 시간 p95`가 스케줄 주기보다 충분히 낮은지 확인합니다.
8. `원자 제거 실패율`과 `락 스킵 수`가 큐 적체와 연결되는지 확인합니다.

### 3.3 1,000명 지속 유입 판단 기준

1,000명 / 3분은 V1 구조의 기본 안정성 확인 구간입니다.

통과 기준:
- `joinQueue` 5xx 에러가 없어야 합니다.
- `joinQueue` p95가 큰 진동 없이 유지되어야 합니다.
- `전체 대기 인원`이 테스트 종료 후 빠르게 0에 가까워져야 합니다.
- `초당 매칭 성사 수`가 약 2.8페어/s 이상을 안정적으로 처리해야 합니다.
- `매칭 성공 유저 대기 시간 p95`가 10초보다 충분히 낮아야 합니다.
- `원자 제거 실패율`은 0에 가까워야 합니다.

해석:
- 이 구간에서 문제가 생기면 구조적 한계보다 설정/테스트 데이터/기본 구현 문제일 가능성이 큽니다.
- 먼저 테스트 유저 중복, Redis 초기화, 인증 실패, API 인스턴스 분산 여부를 확인합니다.

### 3.4 5,000명 지속 유입 판단 기준

5,000명 / 3분은 V1 구조가 중간 규모 운영 유입을 감당할 수 있는지 보는 구간입니다.

통과 기준:
- `joinQueue` p95가 1,000명 대비 완만하게만 증가해야 합니다.
- `초당 매칭 성사 수`가 약 13.9페어/s 이상에 근접해야 합니다.
- `전체 대기 인원`이 계속 우상향하지 않아야 합니다.
- 테스트 종료 후 큐가 회복되는 시간이 과도하게 길지 않아야 합니다.
- `스캔 소요 시간 p95`가 스케줄 간격에 가까워지면 안 됩니다.
- `매칭 성공 유저 대기 시간 p95`가 10초 아래여야 합니다.

해석:
- API p95는 안정적인데 큐가 증가하면 매칭 엔진 처리량이 부족한 것입니다.
- 스캔 티켓 수 증가에 따라 스캔 시간이 크게 늘면 전체 스캔 방식의 비용이 드러나는 구간입니다.
- 이 구간에서만 문제가 생기면 V1은 소규모에는 충분하지만 중간 규모 확장성에는 개선 여지가 있다고 판단합니다.

### 3.5 10,000명 지속 유입 판단 기준

10,000명 / 3분은 V1 구조의 확장 한계를 확인하는 구간입니다.

통과 기준:
- `joinQueue` 5xx 에러가 없어야 합니다.
- `joinQueue` p95가 급격히 상승하지 않아야 합니다.
- `초당 매칭 성사 수`가 약 27.8페어/s에 근접해야 합니다.
- `전체 대기 인원`이 테스트 중 일정 수준에서 안정되거나 테스트 종료 후 빠르게 감소해야 합니다.
- `매칭 성공 유저 대기 시간 p95`가 10초를 넘지 않아야 합니다.
- `스캔 소요 시간 p95/p99`가 스케줄 간격을 지속적으로 침범하지 않아야 합니다.

확장 필요 판단:
- 큐가 테스트 종료 후에도 길게 남습니다.
- 매칭 성공 유저 대기 시간 p95가 10초를 넘습니다.
- 스캔 p95가 스케줄 주기에 가까워지고 락 스킵이 증가합니다.
- 스캔당 로드 티켓 수가 증가할수록 스캔 시간이 비선형으로 증가합니다.
- API p95는 괜찮은데 엔진 지표만 나빠집니다.

이 경우 API 인스턴스 추가보다 매칭 엔진 구조 개선이 우선입니다.

## 4. Spike 테스트 분석 가이드

Spike 테스트는 순간적으로 많은 유저가 매칭 버튼을 누르는 상황을 가정합니다.

현재 기본 시나리오는 `shared-iterations` 방식입니다.

- 1,000명 burst
- 5,000명 burst
- 10,000명 burst

Spike 테스트에서는 순간 응답 시간보다 회복 시간이 더 중요합니다.

### 4.1 분석 순서

1. burst 구간에서 `joinQueue` 요청이 정상적으로 들어갔는지 확인합니다.
2. `joinQueue` 5xx 에러가 발생했는지 확인합니다.
3. `전체 대기 인원`의 최고점을 확인합니다.
4. 큐가 0 또는 기대 잔여치까지 줄어드는 데 걸린 시간을 측정합니다.
5. `초당 매칭 성사 수`가 피크 이후 충분히 올라가는지 확인합니다.
6. `스캔당 로드 티켓 수` 최고점과 `스캔 소요 시간 p95/p99`를 비교합니다.
7. `매칭 성공 유저 대기 시간 p95/p99`가 얼마나 튀는지 확인합니다.
8. `락 스킵 수`가 회복 지연과 연결되는지 확인합니다.

### 4.2 Spike에서 반드시 기록할 값

각 실행마다 아래 값을 기록합니다.

| 항목 | 의미 |
| --- | --- |
| 요청 시작 시각 | spike 시작 시간 |
| 요청 종료 시각 | k6가 joinQueue 요청을 모두 보낸 시간 |
| 큐 최고점 | Redis 대기열이 가장 많이 쌓인 순간 |
| 큐 소진 시각 | `match_queue_size`가 0 또는 기대 잔여치에 도달한 시간 |
| 큐 소진 시간 | 요청 종료 후 큐가 비워지는 데 걸린 시간 |
| joinQueue p95/p99 | API 진입 경로 지연 |
| 스캔 p95/p99 | 엔진 스캔 비용 |
| 매칭 대기 p95/p99 | 사용자 체감 대기 시간 |
| 원자 제거 실패율 | 동시성/상태 불일치 여부 |
| 분당 락 스킵 수 | 멀티 인스턴스 엔진 경합 |

### 4.3 1,000명 Spike 판단 기준

1,000명 spike는 기본 burst 처리 능력 확인 구간입니다.

통과 기준:
- `joinQueue` 5xx가 없어야 합니다.
- 큐가 빠르게 쌓인 뒤 짧은 시간 안에 감소해야 합니다.
- `초당 매칭 성사 수`가 spike 직후 상승해야 합니다.
- `스캔 소요 시간 p95/p99`가 크게 튀지 않아야 합니다.
- `매칭 성공 유저 대기 시간 p95`가 10초 아래여야 합니다.

해석:
- 여기서 큐 소진이 느리면 V1 엔진의 기본 처리량이나 스케줄 설정을 먼저 점검합니다.

### 4.4 5,000명 Spike 판단 기준

5,000명 spike는 순간 대기열이 커질 때 전체 스캔 방식이 버티는지 확인하는 구간입니다.

통과 기준:
- API는 요청을 대부분 받아야 합니다.
- 큐 최고점 이후 감소 추세가 명확해야 합니다.
- `스캔당 로드 티켓 수` 증가에 비해 `스캔 소요 시간` 증가가 과도하지 않아야 합니다.
- `매칭 성공 유저 대기 시간 p95`가 10초를 넘지 않아야 합니다.
- 원자 제거 실패율이 낮아야 합니다.

해석:
- 큐는 줄지만 대기 시간 p95가 높으면 사용자 경험상 위험합니다.
- 스캔 시간이 길어지면서 락 스킵이 증가하면 멀티 인스턴스에서 실제 엔진 처리 기회가 줄어드는지 봐야 합니다.

### 4.5 10,000명 Spike 판단 기준

10,000명 spike는 V1 구조의 한계와 V2 전환 필요성을 보는 구간입니다.

통과 기준:
- API 5xx가 없어야 합니다.
- 큐가 계속 남아 정체되지 않아야 합니다.
- 큐 소진 시간이 운영상 허용 가능한 범위여야 합니다.
- `매칭 성공 유저 대기 시간 p95`가 10초 이하를 유지해야 합니다.
- p99가 일시적으로 튀더라도 테스트 종료 후 정상 범위로 회복되어야 합니다.

확장 필요 판단:
- 큐 소진 시간이 길어지고 다음 테스트 시작 전까지 잔여 큐가 남습니다.
- 매칭 대기 p95가 10초를 넘습니다.
- 스캔 p99가 반복적으로 커지고 스캔 주기를 침범합니다.
- 스캔당 티켓 수가 많아질수록 매칭 성사 수가 비례해서 증가하지 않습니다.
- API는 정상인데 엔진이 큐를 따라가지 못합니다.

이 경우 단순히 API 인스턴스를 늘리는 것으로 해결되지 않습니다. 현재 구조에서는 전역 락 때문에 동시에 여러 인스턴스가 매칭 엔진을 병렬로 돌 수 없고, 한 번에 전체 대기열을 로드하는 비용도 계속 커집니다.

## 5. 확장 여부 판단 기준

### 5.1 API 인스턴스 확장이 필요한 경우

다음 조건이면 API 인스턴스 확장을 먼저 검토합니다.

- `joinQueue` p95/p99가 증가합니다.
- HTTP 5xx가 발생합니다.
- 두 인스턴스 중 한쪽에 요청이 몰립니다.
- JVM thread, connection pool, Redis connection 사용량이 포화됩니다.
- 엔진 지표는 안정적인데 API 지표만 나빠집니다.

대응:
- 로드밸런싱 확인
- API 인스턴스 추가
- Redis connection pool 조정
- 인증/DB 조회 경로 최적화

### 5.2 매칭 엔진 확장이 필요한 경우

다음 조건이면 매칭 엔진 구조 개선을 먼저 검토합니다.

- `joinQueue`는 정상인데 `match_queue_size`가 계속 증가합니다.
- `초당 매칭 성사 수`가 필요 페어/s보다 낮습니다.
- `매칭 성공 유저 대기 시간 p95`가 10초에 가까워지거나 초과합니다.
- `스캔 소요 시간 p95/p99`가 스케줄 주기를 침범합니다.
- `스캔당 로드 티켓 수`가 증가할수록 스캔 시간이 비선형으로 증가합니다.
- 락 스킵 증가가 큐 적체와 함께 나타납니다.

대응:
- 전체 스캔 범위 축소
- 티어별 또는 구간별 부분 스캔
- 매칭 엔진 독립 worker 분리
- 엔진 샤딩 전략 검토
- 후보 탐색 알고리즘 개선
- 후처리 재시도/보상 처리 추가

### 5.3 Redis 병목을 의심해야 하는 경우

다음 조건이면 Redis 병목을 확인합니다.

- API p95와 엔진 스캔 시간이 동시에 증가합니다.
- `atomicPairRemove` 시도 수 대비 지연이 커집니다.
- Redis command latency가 증가합니다.
- Redis CPU 또는 메모리 사용량이 높습니다.
- 큐 크기 gauge 조회도 느려집니다.

대응:
- Redis latency 확인
- ZSET 크기와 key 분포 확인
- 파이프라이닝 효과 확인
- Lua 스크립트 실행 시간 확인
- Redis 인스턴스 스펙 또는 분리 검토
